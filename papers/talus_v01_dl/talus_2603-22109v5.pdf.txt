TALUS: FIPS-204-Exact Threshold ML-DSA via
Boundary Clearance
Leo Kao and Raymond Chang
Codebat Technologies Inc.
Abstract.We present TALUS, a threshold signing protocol for ML-DSA (FIPS 204)
that supports anarbitrarynumber of parties, outputs a stock FIPS-204 public key and
signatures accepted by any unmodified ML-DSA verifier, and reduces, for a bounded number
of signatures per key, to ML-DSA’s own assumptions (Module-LWE and SelfTargetMSIS).
Its core is theBoundary Clearance Condition(BCC): for a constant fraction of nonces (31.7%
at ML-DSA-65), the secret vectors2 provably cannot cross a rounding boundary, so the
s2-dependent rejection check can be enforced offline on preprocessed nonces. This removes
the interaction that forces multi-round signing in prior schemes, yielding a TEE-assisted
one-round profile and a fully distributed honest-majority MPC profile with two online rounds,
both built on a Carry Elimination Framework for the commitmentHighBits(A y), a step we
show is unavoidable (the MPC profile computes it on secret shares, the TEE profile inside
the enclave).
We prove a lower bound: any FIPS-204-exact threshold scheme revealing a summed (Irwin–
Hall) nonce admits an efficient key-recovery attack after about230 signatures under one key
(at ML-DSA-65), so noqs-independent unforgeability is possible for this class. A matching
qs-bounded analysis certifies over105bits at the operational signing cap for the external view,
with insider ceilings disclosed per view. Moving thes2-rejection offline leaves a residuals2
channel; we identify and price its strongest key-recovery ourselves—a meet-in-the-middle over
the public-cokernel syndrome—and place a mandatory key-rotation cap (≈214 signatures)
so that this channel islattice-shielded: its strongest known attack is modeled to cost the
standard Module-LWE bound, with an unconditional meet-in-the-middle floor of≈258/249
proven below it. A Rust implementation across all three FIPS 204 levels demonstrates
practicality.1

1 Introduction
Post-quantum migration is turning ML-DSA (FIPS 204 [Nat24]) into the default signature for
high-assurance deployments: certificate authorities, hardware security modules, and enterprise
key custody. Many of these settings needthresholdsigning (splitting the signing key acrossN
parties so that anyT can sign while fewer thanT shares alone do not reconstruct it) while still
emitting signatures that existing verifiers accept without modification. Threshold ML-DSA is
therefore both practically pressing and technically awkward: unlike Schnorr, ML-DSA’s signing
loop contains asecret-dependent rejection check, and evaluating it on secret shares is what makes
prior FIPS-compatible threshold schemes multi-round.2 These schemes trade the online round
count against the party scale they reach. The low-round options cap at a handful of parties, while
the ones that scale to many parties pay many online rounds per signature (Table 1). TALUS

BCC has no benefit for a single signer: there, ther0 check is free (one resamplesylocally), so

same check otherwise costs a multi-round MPC ons2. Offline nonce selection for single-party
Dilithium has been explored [YLW25], but for a different rejection condition and by filtering the

we formalize for this setting rather than claim as new.
The cost of exactness.Keeping FIPS-204-exact outputs and verifier compatibility has a price
that we make precise rather than hide. In the threshold setting the nonce is asumof the parties’

by changing the distribution (non-FIPS); TALUS instead accepts aqs-bounded guarantee and
pairs it with a mandatory keyrotation(fresh key generation to a new public key) that caps a

2.4 Security definitions
Definition 1(qs-bounded EUF-CMA, threshold).For a query boundqs, a(T,N )-threshold

We treat static corruption throughout; adaptive corruption is left open. Definition 1 explicitly
grants the adversary the pre-message transcript, so that a proof under it must handle values
(such as an offline commitment) that are fixed before the message, the setting relevant to §8.

4 The Boundary Clearance Condition
This section defines BCC, proves that it makes the secret-dependent rejection check redundant,
and records its acceptance rate. The per-coefficient geometry is the Dilithium hint-correctness
lemma; the contribution is the observation that the resulting condition is key- and message-
independent, hence enforceable offline, and that enforcing it lets a threshold scheme delete the
distributeds 2 computation rather than perform it.

4.3 Key- and message-independence, and where the value lies
BCC depends only onA y. Both inputs are independent of the long-term secret:Ais public, and

7.2 Why two rounds, and why standard assumptions
The timing of thew1 reveal is exactly what separates a secure standard-assumption protocol
from an insecure one.
• If w1 is revealedoffline, before µ(a one-round online phase), then corrupt parties hold the
offline commitments before choosing messages, the commit-before-message setting underlying
ROS/Wagner attacks on rejection-based threshold signatures [Wag02, DEF+19, BLL+21]. A
standard reduction cannot then program the challenge, and security would need a one-more
assumption.
• If w1 is keptcommitted/shared until onlineandopenedonly after µ(the two-round phase
above), each session’sw1 is revealed only after that session’s message is fixed, so a reduction
need not program the challenge ahead of the message and security rests on standard Module-
LWE and SelfTargetMSIS (§8) in the sequential/bounded-qs setting. The commitmenttiming
removes the one-more requirement for a single session; it doesnot, by itself, defeat aconcurrent
ROS/Wagner adversary, since a commit-then-open with no per-session binding factor is exactly
the setting of [DEF+19]. TALUS has no binding-factor analogue to add—FIPS-exactness fixes
c =H(µ∥w1)with no per-session term to absorb (cf. the reused-nonce discussion below)—so
full concurrency is not claimed and unforgeability isqs-bounded. What blocks adirecttransfer
of the Schnorr-style ROS/Wagner attack is the non-homomorphism ofHighBits (c is applied
to a non-linear function of the nonce, §9), and any forgery would still have to be a short
SelfTargetMSIS solution.
This is the same axis that makes the TEE profile one round: the enclave holds the aggregate in
the clear, so it can apply the BCC filter and be ready to releasew1 immediately onceµarrives,
collapsing the reveal into the single online round, whereas the MPC profile has no such trusted
party and must run the commit-then-open across the two rounds. In both profilesw1 is revealed
only afterµ; what the enclave saves is the extra online round the distributed open would otherwise
cost. TALUS-MPC adopts the two-round ordering: keeping the headline standard-assumption
is worth one online round. The one-round MPC variant (secure only under a one-more lattice

We state the boundaries of the results plainly.
